# embed-server Baseline — 2026-04-16

**Host**: Oracle Cloud ARM Neoverse-N1, 4 vCPU, Ubuntu 24.04
**Container limits**: 2 GB RAM, 4 CPU (no quota)
**Model**: `multilingual-e5-large` (1024 dim, 256 max tokens, `model_quantized.onnx`)
**Server config**: Rust embed-server, `Mutex<Session>` serialization, `intra_threads=4`, ONNX Runtime 1.24.3 (load-dynamic)

## Results — medium Russian text (8 texts per request)

The standard bench scenarios (c=1..40, 20..40 iters) were attempted but c>=4 with 40 iterations
causes timeouts because `Mutex<Session>` serializes all ONNX inference. At ~2.8s p50 per request,
request #23+ in a serialized queue waits >120s and triggers urllib timeout.

## Notes

- Sequential p50 = 2789 ms -> per-text = 349 ms.
- Concurrent growth pattern: flat throughput (~0.33-0.35 tps) at all concurrency levels — the
  `Mutex<Session>` fully serializes ONNX inference. Concurrency only adds queueing latency: c=4
  p50=11255ms (~4x sequential), c=10 p50=19045ms (~7x). TPS does not increase with more workers.
- Error rate: 0 (within safe iteration counts).
- Timeouts: bench.py's standard 40-iteration scenarios at c>=4 all produce urllib TimeoutError at
  120s; this is expected behavior for a single-mutex server. The standard `bench.py` script's
  scenarios (c=4..40 x 40 iters) are unrunnable until the mutex is replaced with a batcher/pool.
- Single-request throughput: ~0.18 req/s (5.4s raw single-call with 8 texts, measured with curl).

## Purpose

Captured BEFORE the plan's changes (batcher, metrics, backpressure, graceful shutdown, jina-code-v2 second model). Subsequent tasks must not regress these numbers. Post-optimization bench will compare against this file.

The primary bottleneck is `Mutex<Session>` — replacing it with a request batcher or session pool
should raise throughput from 0.35 tps to near CPU-bound limits (expected 4-8x with batcher).
